## CASO 1: ¿Cuáles son las diferencias arquitectónicas, eléctricas y de propósito entre Arduino (ATmega328P), ESP32-S3, Raspberry Pi 5 y NVIDIA Jetson Orin Nano?

En el laboratorio de ingeniería y robótica, la selección de la placa de desarrollo depende de si el requerimiento es control en tiempo real determinista a nivel de registros, conectividad inalámbrica en el borde (*Edge IoT*), procesamiento computacional de propósito general o aceleración de inteligencia artificial:

### Comparativa Arquitectónica y Eléctrica:

| Parámetro | [[Arduino_Uno_R3]] | [[ESP32-S3]] | [[Raspberry_Pi_5]] | [[NVIDIA_Jetson_Orin_Nano]] |
| :--- | :--- | :--- | :--- | :--- |
| **Tipo de Procesador** | Microcontrolador ([[MCU]]) | Microcontrolador ([[MCU]]) | Microcomputador ([[SBC]]) | Módulo de Cómputo IA ([[SOM]]) |
| **Arquitectura** | 8-bit AVR ([[ATmega328P]]) | 32-bit Xtensa LX7 Dual-Core | 64-bit ARM Cortex-A76 Quad | 64-bit ARM Cortex-A78AE 6-Core |
| **Frecuencia Reloj** | 16 MHz | Hasta 240 MHz | 2.4 GHz | Hasta 1.5 GHz |
| **Memoria RAM** | 2 KB SRAM | 512 KB SRAM (+ 8MB PSRAM) | 4 GB u 8 GB LPDDR4X | 4 GB u 8 GB LPDDR5 (68 GB/s) |
| **GPU / IA** | Ninguna | Instrucciones SIMD / Vectoriales | VideoCore VII (OpenGL/Vulkan) | GPU NVIDIA Ampere (1024 CUDA Cores + 32 Tensor Cores) |
| **Voltaje Lógico GPIO** | **5.0 V** (Tolerante) | **3.3 V** (No tolerante a 5V) | **3.3 V** (No tolerante a 5V) | **3.3 V / 1.8 V** (No tolerante a 5V) |
| **Sistema Operativo** | Código Bare-Metal / C++ | FreeRTOS nativo / ESP-IDF | Linux ([[Raspberry_Pi_OS]]) | Linux for Tegra ([[L4T]] / Ubuntu 22.04 LTS) |
| **Alimentación Típica** | 7-12V (Vin) o 5V USB (0.2W) | 5V USB (0.5W - 1W) | 5V / 5A USB-C PD (15W - 25W) | 9V - 20V DC Barrel Jack (7W - 15W) |

### Criterio de Selección Operativo:
1. **Arduino Uno / Nano**: Muestreo analógico simple, control de relés y actuadores donde se requiera robustez eléctrica de 5V y tolerancia a sobretensiones accidentales.
2. **ESP32-S3**: Nodos de sensores remotos [[IoT]], transmisión de telemetría por [[MQTT]] con cifrado [[TLS_1.3]], periféricos capacitivos y visión por cámara ([[OV2640]]) de bajo costo.
3. **Raspberry Pi 5**: Servidor local de laboratorio, brokers Mosquitto centrales, pasarelas web, firmware de control de cinemática [[Klipper]] y controladores de visión básica.
4. **NVIDIA Jetson Orin Nano**: Inferencia de modelos de visión artificial en tiempo real (detección de objetos YOLO a 60 FPS, segmentación semántica) y robótica autónoma con ROS 2 ([[Robot_Operating_System]]).

## CASO 2: ¿Cómo detectar, diagnosticar permisos y conectarse por terminal a cualquier placa serial (ESP32, Arduino, STM32) en Linux (Bash) sin entornos gráficos?

En sistemas operativos [[Linux]], el kernel expone los convertidores USB a UART (chips [[CH340]], [[CP2102]], [[FT232R]] o USB CDC nativo) bajo el subsistema `tty`.

### 1. Monitoreo en Tiempo Real de la Conexión Física:
Abre una terminal y ejecuta el visor de eventos del kernel antes de enchufar la placa:
```bash
sudo dmesg -wH
```
Al conectar el dispositivo, el subsistema USB emitirá trazas similares a:
`usb 1-2: ch341-uart converter now attached to ttyUSB0` o `cdc_acm 1-2:1.0: ttyACM0: USB ACM device`.

### 2. Identificación Inmutable por Identificador de Hardware (/dev/serial/by-id/):
Nunca se debe fiar de nombres volátiles como `/dev/ttyUSB0` o `/dev/ttyUSB1`, ya que su orden cambia si se reinicia el equipo con múltiples placas conectadas. Se utiliza la ruta canónica por identificador de hardware:
```bash
ls -la /dev/serial/by-id/
# Salida: usb-Silicon_Labs_CP2102_USB_to_UART_Bridge_Controller_0001-if00-port0 -> ../../ttyUSB0
```

### 3. Solución Definitiva de Permisos sin 'chmod 777' (Grupo dialout y Reglas udev):
```bash
# Añadir el usuario al grupo con privilegios sobre la interfaz serial
sudo usermod -aG dialout $USER
newgrp dialout

# Crear regla udev para garantizar permisos 0666 a programadores USB (ejemplo CH340: Vendor 1a86, Product 7523)
sudo tee /etc/udev/rules.d/99-serial-lab.rules << 'EOF'
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", MODE="0666", GROUP="dialout"
SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", MODE="0666", GROUP="dialout"
EOF
sudo udevadm control --reload-rules && sudo udevadm trigger
```

### 4. Conexión de Terminal por Terminal CLI:
Utilizando herramientas especializadas de consola:
```bash
# Con picocom (Recomendado para desarrollo de microcontroladores):
# --echo-newline (-c): emula retorno de carro
# Para salir: Ctrl+A seguido de Ctrl+X
picocom -b 115200 /dev/serial/by-id/usb-Silicon_Labs_CP2102* -c

# Con screen (Alternativa universal instalada por defecto):
# Para salir: Ctrl+A seguido de '\' (confirmar con 'y')
screen /dev/ttyUSB0 115200
```

## CASO 3: ¿Cómo detectar y abrir una consola serial con una placa de desarrollo en macOS (Zsh) y cuál es la diferencia crítica entre los dispositivos /dev/tty.* y /dev/cu.*?

En [[macOS]] (basado en el kernel Darwin/BSD), la pila de controladores seriales implementa una distinción histórica de telefonía y módems que causa bloqueos comunes si no se comprende adecuadamente.

### 1. La Diferencia Crítica: `/dev/tty.*` frente a `/dev/cu.*`:
- **`/dev/tty.usbserial-*` (Teletype / Inbound)**: Diseñado históricamente para recibir llamadas telefónicas entrantes en módems. Al abrir este descriptor en el sistema operativo, la llamada bloquea el proceso hasta que la línea de hardware detecta la señal [[DCD]] (*Data Carrier Detect*). En un microcontrolador que no maneja señal DCD por hardware, abrir este puerto deja la terminal permanentemente congelada.
- **`/dev/cu.usbserial-*` (Calling Unit / Outbound)**: Diseñado para realizar llamadas salientes. **Ignora por completo la señal DCD** y abre el descriptor de archivo de forma inmediata sin esperar señales de portadora telefónica. **En macOS se debe usar siempre `/dev/cu.*` para conectar a microcontroladores.**

### 2. Detección de Dispositivos Conectados en Terminal (Zsh):
```bash
# Listar todas las interfaces seriales USB Calling Unit conectadas
ls -la /dev/cu.*
# Salidas típicas:
# /dev/cu.usbserial-0001 (Controladores FTDI / Silicon Labs CP2102)
# /dev/cu.usbmodem1101   (Arduino Uno R4 / ESP32-S3 USB CDC nativo)
# /dev/cu.wchusbserial*  (Controladores económicos CH340)

# Inspeccionar árbol de dispositivos USB a nivel de hardware en macOS:
system_profiler SPUSBDataType | grep -A 8 -B 2 -E 'CH340|CP210|FT232|USB Serial'
```

### 3. Apertura de Terminal de Telemetría con Screen:
```bash
# Conexión a 115200 baudios
screen /dev/cu.usbserial-0001 115200
```

### 4. Salida Limpia para Evitar el Bloqueo del Puerto ('Resource Busy'):
Si cierras la ventana de la terminal de macOS sin desconectar `screen`, el proceso queda huérfano y retiene el descriptor con el error `Resource busy`.
- **Salida correcta**: Presiona la combinación `Ctrl + A` y luego escribe `\` (barra invertida), confirmando con `y`.
- **Recuperación si el puerto quedó tomado**: Busca el PID del proceso colgado y termínalo:
```bash
lsof | grep /dev/cu.usbserial
kill -9 <PID_DETECTADO>
```

## CASO 4: ¿Cómo interactuar con placas seriales en Windows mediante PowerShell sin software de terceros, y cómo puentear dispositivos USB físicos hacia WSL2 con usbipd?

En entornos de desarrollo sobre [[Windows]], la interacción con placas embebidas puede realizarse de forma nativa en [[PowerShell]] o canalizándola hacia máquinas virtuales [[WSL2]] mediante redirección de bus USB sobre IP.

### 1. Detección de Puertos COM en PowerShell:
```powershell
# Inspeccionar puertos COM activos y descripción de controladores Plug-and-Play
Get-PnpDevice -Class 'Ports' -Status OK | Select-Object Name, DeviceID

# Obtener únicamente los nombres de puerto serial disponibles en .NET
[System.IO.Ports.SerialPort]::GetPortNames()
```

### 2. Lectura y Escritura por Terminal Nativa en PowerShell (.NET):
```powershell
$portName = "COM4"
$baudRate = 115200
$serial = New-Object System.IO.Ports.SerialPort $portName, $baudRate, [System.IO.Ports.Parity]::None, 8, [System.IO.Ports.StopBits]::One
$serial.ReadTimeout = 3000

try {
    $serial.Open()
    Write-Host "[CONECTADO] Escuchando telemetría en $portName... (Ctrl+C para detener)"
    while ($true) {
        try {
            $line = $serial.ReadLine()
            Write-Host "[TELEMETRÍA] $line"
        } catch [TimeoutException] {
            # Continuar esperando datos si el microcontrolador envía de forma esporádica
        }
    }
} finally {
    $serial.Close()
    $serial.Dispose()
    Write-Host "[INFO] Puerto serial cerrado de forma segura."
}
```

### 3. Conexión y Puenteo de Dispositivos USB hacia WSL2 con `usbipd-win`:
Para programar un ESP32 o Arduino con herramientas de Linux (`esptool.py`, `avrdude`) directamente dentro de WSL2:

1. **En PowerShell con privilegios de Administrador (Host Windows)**:
```powershell
# Listar dispositivos USB conectados y sus identificadores de bus (BUSID)
usbipd list

# Vincular el bus del adaptador serial (ejemplo BUSID 1-4)
usbipd bind --busid 1-4

# Adjuntar el dispositivo a la instancia activa de WSL2
usbipd attach --wsl --busid 1-4
```

2. **Dentro de la terminal de WSL2 (Linux)**:
```bash
# Verificar que el hardware USB fue transferido al kernel de Linux en WSL2
lsusb
ls -la /dev/ttyUSB* /dev/ttyACM*
```

3. **Desconexión al terminar (en Windows)**:
```powershell
usbipd detach --busid 1-4
```

## CASO 5: Explica el peligro de conectar un Arduino de 5V a un ESP32 o Raspberry Pi de 3.3V, y cómo diseñar un convertidor de nivel lógico (Level Shifter) con MOSFETs BSS138 o divisores resistivos.

Los microcontroladores y computadores monoplaca modernos ([[ESP32]], [[Raspberry_Pi]], [[STM32]], [[RP2040]]) operan con lógica [[CMOS]] de **3.3 V** (o inferior). Sus pines de entrada y salida ([[GPIO]]) integran diodos internos de protección contra descargas electrostáticas ([[ESD]]) conectados entre el pin y el riel $V_{DD}$ (3.3V).

### Mecanismo Físico de Destrucción Eléctrica:
Si se conecta directamente una salida digital en estado ALTO de 5V (ej. el pin TX de un [[Arduino_Uno]]) a un pin de 3.3V de un ESP32:
1. El voltaje de 5V supera el potencial de ruptura del diodo de fijación interno ($V_{DD} + 0.3\text{V} = 3.6\text{V}$).
2. El diodo entra en conducción directa no controlada, derivando corrientes destructivas (de decenas a cientos de miliamperios) hacia el regulador interno de 3.3V.
3. Se produce una avalancha térmica (*Thermal Runaway*) o ruptura dieléctrica de la compuerta de óxido de silicio ([[SiO2]]), destruyendo permanentemente el pin GPIO o quemando el procesador.

### Solución 1: Divisor de Tensión Resistivo (Unidireccional - ej. Señales TX de 5V a RX de 3.3V):
Para señales unidireccionales de baja a media frecuencia (como líneas UART):
```text
Señal 5V (TX Arduino) ----[ R1: 1.8 kΩ ]----+----> Señal 3.3V (RX ESP32)
                                             |
                                        [ R2: 3.3 kΩ ]
                                             |
                                            GND (Tierra común obligatoria)
```
Cálculo analítico por ley de Ohm:
$$V_{out} = V_{in} \cdot \frac{R_2}{R_1 + R_2} = 5.0\text{ V} \cdot \frac{3300}{1800 + 3300} = 5.0 \cdot \frac{3300}{5100} \approx 3.235\text{ V}$$
Este valor se sitúa dentro de la región segura de nivel lógico alto ($0.7 \cdot V_{DD} \le V_{IH} \le V_{DD}$).

### Solución 2: Convertidor Bidireccional Activo con MOSFET ([[BSS138]]) para buses I2C:
En buses bidireccionales con drenador abierto ([[Open-Drain]]) como [[I2C]] (líneas SDA y SCL), un divisor resistivo falla porque la línea debe transmitir en ambos sentidos. Se utiliza un transistor MOSFET de canal N:
```text
             3.3V (LV)                         5.0V (HV)
                |                                 |
             [10kΩ]                            [10kΩ]
                |                                 |
Línea 3.3V <----+--- (Source) [ MOSFET N ] (Drain) +----> Línea 5.0V
                              (Gate) |
                                     |
                                    3.3V
```

- **Estado Reposo (Ambos lados en ALTO)**: La compuerta (Gate) y la fuente (Source) están a 3.3V ($V_{GS} = 0\text{V}$). El transistor está en corte; cada línea se eleva a su respectivo riel mediante sus resistencias pull-up.
- **El lado de 3.3V conmuta a BAJO (0V)**: $V_S = 0\text{V}$, $V_G = 3.3\text{V} \implies V_{GS} = 3.3\text{V} > V_{th}$. El canal se activa y drena la línea de 5V a tierra (0V).
- **El lado de 5V conmuta a BAJO (0V)**: El diodo de cuerpo (*body diode*) del MOSFET entra en conducción polarizado en directa, bajando el lado de 3.3V a ~0.6V; inmediatamente $V_{GS}$ supera el umbral y el canal N se satura, llevando el lado de 3.3V a 0V pleno.

## CASO 6: ¿Cómo configurar y depurar una placa NVIDIA Jetson (Orin Nano / Nano) mediante su puerto serie UART de depuración y flashearla en modo Force Recovery?

Las plataformas de cómputo embebido [[NVIDIA_Jetson]] no utilizan BIOS convencional x86, sino un microcódigo de arranque escalonado ([[Tegra_Bootloader]]) gestionado por microcontroladores internos (*Boot ROM* -> *Tegra Bootloader* -> *UEFI* -> *Kernel Linux*).

### 1. Conexión a la Consola Serial de Depuración (UART Debug Header):
En caso de que el sistema operativo no arranque la interfaz de red o el servidor gráfico X11/Wayland colapse, la consola serie expone todos los mensajes de arranque del kernel antes del init de systemd:

- **Cabecera de Pines de Depuración (ej. J44 o conector de 12 pines según placa)**:
  - Pin TX de la Jetson $\rightarrow$ Pin RX del convertidor USB-TTL (3.3V).
  - Pin RX de la Jetson $\rightarrow$ Pin TX del convertidor USB-TTL (3.3V).
  - Pin GND de la Jetson $\rightarrow$ Pin GND del convertidor (Tierra de referencia obligatoria).
  - **¡NUNCA conectar el pin VCC/5V del cable!** Se alimenta la Jetson exclusivamente por su conector DC dedicado.

Parámetros de conexión serial:
- Baudios: **115200**
- Bits de datos: **8**, Paridad: **Ninguna**, Bits de parada: **1**, Control de flujo: **Ninguno**.
Comando en Linux/macOS: `picocom -b 115200 /dev/ttyUSB0` o `screen /dev/cu.usbserial-0001 115200`.

### 2. Procedimiento para Entrar en Modo 'Force Recovery' (Flasheo de Firmware):
El modo de recuperación por hardware permite transferir la imagen base del sistema operativo [[JetPack]] y el árbol de dispositivos ([[Device_Tree]] / `.dtb`) desde una computadora host (Ubuntu x86_64) hacia el chip eMMC o unidad NVMe M.2:

1. Apagar la alimentación eléctrica de la Jetson.
2. Localizar la cabecera de botones de la placa (Header de pines para Power, Reset y Recovery).
3. Conectar mediante un puente físico (*jumper*) el pin **FC REC** (*Force Recovery*) con **GND**.
4. Conectar el cable USB de datos (USB-C o Micro-USB) desde el puerto OTG de la Jetson hacia la PC host.
5. Aplicar alimentación eléctrica (botón Power).
6. Retirar el jumper entre FC REC y GND tras 2 segundos.

### 3. Verificación en la Computadora Host Linux:
```bash
# Verificar que el chip de NVIDIA Tegra fue reconocido en modo APX Recovery
lsusb | grep -i 'Nvidia Corp.'
# Salida esperada: ID 0955:7023 NVidia Corp. (El ID de producto varía según el chip Orin/Xavier/Nano)
```

Una vez verificado el ID `0955:XXXX`, se puede ejecutar el script de flasheo del SDK Manager o la utilidad por línea de comandos:
```bash
sudo ./flash.sh jetson-orin-nano-devkit mmcblk0p1
```
