## MÓDULO 1: ¿Cómo estructurar un script de Bash con estándar de producción seguro mediante set -euo pipefail y tramas de limpieza (traps)?

En automatización industrial, un script de [[Bash]] sin configuración defensiva puede ejecutar comandos erróneos si una variable no está inicializada o una tubería intermedia falla silenciosamente. El estándar defensivo exige `set -euo pipefail` y manejo determinista de señales con `trap`.

```bash
#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t' # Previene división de palabras involuntaria en variables

readonly SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
readonly TEMP_DIR="$(mktemp -d -t sentinel_job_XXXXXX)"
readonly LOG_FILE="${SCRIPT_DIR}/system_audit.log"

cleanup() {
    local exit_code=$?
    echo "[INFO] Ejecutando rutina de limpieza en: ${TEMP_DIR}" >&2
    rm -rf "${TEMP_DIR}"
    exit "${exit_code}"
}
trap cleanup EXIT INT TERM HUP

log() {
    local msg="$1"
    echo "[$(date --iso-8601=seconds)] [INFO] ${msg}" | tee -a "${LOG_FILE}"
}

audit_directory() {
    local target_dir="${1:-/var/log}"
    log "Iniciando inspección en: ${target_dir}"
    find "${target_dir}" -type f -name "*.log" -print0 | \
        xargs -0 -I {} bash -c 'gzip -t "$1" 2>/dev/null || echo "Archivo corrupto: $1"' _ {}
}

audit_directory "/var/log"
log "Auditoría finalizada satisfactoriamente."
```

Al registrar `trap cleanup EXIT`, la limpieza de directorios temporales se garantiza sin importar si el script culmina con éxito o por un error fatal.

## MÓDULO 2: ¿Cómo configurar la interoperabilidad entre Windows 11 y WSL2 (Windows Subsystem for Linux), controlando los límites de RAM y los puentes de red?

[[WSL2]] opera como una máquina virtual ligera sobre el hipervisor [[Hyper-V]], con su propio kernel Linux real e interfaces de red virtualizadas (`vEthernet`). Para un uso óptimo en laboratorios de desarrollo y evitar que el compilador o PyTorch agoten la memoria de Windows, se debe configurar `.wslconfig` y `/etc/wsl.conf`.

### 1. Configuración del host en Windows (`%USERPROFILE%\.wslconfig`)
```ini
[wsl2]
memory=8GB                   # Techo máximo de RAM para el kernel Linux
processors=6                 # Límite de núcleos lógicos asignados
swap=4GB                     # Archivo de paginación de seguridad
networkingMode=mirrored      # Comparte la interfaz localhost con Windows 11
autoMemoryReclaim=gradual    # Devuelve RAM no utilizada al host de Windows
```

### 2. Configuración dentro de la distribución Linux (`/etc/wsl.conf`)
```ini
[boot]
systemd=true                 # Habilita el init systemd moderno

[automount]
enabled=true
options="metadata,umask=22,fmask=11"
mountFsTab=true
root=/mnt/

[interop]
enabled=true
appendWindowsPath=false      # Evita que ejecutables de Windows colisionen en el PATH de Linux
```

### 3. Comandos de interoperabilidad
- Traducción de rutas: `wslpath -u 'C:\Users\mauro\Desktop'` -> `/mnt/c/Users/mauro/Desktop`.
- Reinicio completo del subsistema desde PowerShell: `wsl --shutdown`.

## MÓDULO 3: ¿Cuáles son las diferencias críticas en la gestión de procesos en segundo plano entre Linux (systemd) y macOS (launchd)?

En sistemas operativos basados en [[POSIX]], la arquitectura del proceso inicial (`PID 1`) difiere radicalmente entre Linux y macOS:

1. **Linux ([[systemd]])**:
   - Agrupa procesos en [[cgroups]] para auditar y limitar cuotas de CPU, memoria y E/S de disco.
   - Emplea archivos declarativos `.service` en `/etc/systemd/system/`:
```ini
[Unit]
Description=Servicio de Telemetría STEM
After=network.target

[Service]
Type=simple
ExecStart=/usr/bin/python3 /opt/telemetry/main.py
Restart=always
RestartSec=3
StandardOutput=journal

[Install]
WantedBy=multi-user.target
```
   - Control: `systemctl start telemetry.service` y supervisión con `journalctl -u telemetry -f`.

2. **macOS ([[launchd]])**:
   - Arquitectura basada en eventos (*event-driven*) de Darwin/BSD. No utiliza archivos INI, sino listas de propiedades en formato XML (`.plist`) en `/Library/LaunchDaemons/`:
```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>org.sentinel.telemetry</string>
    <key>ProgramArguments</key>
    <array>
        <string>/usr/local/bin/python3</string>
        <string>/opt/telemetry/main.py</string>
    </array>
    <key>KeepAlive</key>
    <true/>
    <key>StandardErrorPath</key>
    <string>/var/log/sentinel_err.log</string>
</dict>
</plist>
```
   - Control: `launchctl load /Library/LaunchDaemons/org.sentinel.telemetry.plist`.

## MÓDULO 4: ¿Cómo diagnosticar conexiones de red, sockets abiertos y puertos en escucha mediante ss y netstat en terminales Linux?

En distribuciones Linux modernas, la utilidad `netstat` está deprecada debido a su lentitud al escanear `/proc/net`. Se utiliza [[ss]] (*Socket Statistics*), el cual interactúa directamente con la infraestructura Netlink del kernel para recuperar información atómica de la pila [[TCP]] e [[UDP]].

```bash
# 1. Listar todos los sockets TCP y UDP en estado de escucha con procesos y números de puerto
# -t: TCP, -u: UDP, -l: En escucha (listening), -n: Numérico (sin resolución DNS), -p: Muestra PID y nombre de proceso
sudo ss -tulnp

# 2. Filtrar puertos específicos (ej. broker MQTT 1883 o servidor GGUF 8080)
sudo ss -tuln 'sport = :1883 or sport = :8080'

# 3. Inspeccionar conexiones TCP activas y estadísticas de congestión (RTT, cwnd)
sudo ss -ti

# 4. Identificar sockets en estado TIME_WAIT o CLOSE_WAIT para detectar fugas de sockets
ss -s
```

El comando `ss -ti` expone métricas internas del algoritmo de control de congestión (como Cubic o BBR), indicando el tiempo de ida y vuelta (*Round-Trip Time*, RTT) exacto a nivel de paquete.

## MÓDULO 5: ¿Cómo manipular puertos serie COM en Windows PowerShell para depurar microcontroladores ESP32 y Arduino sin instalar software gráfico?

En Windows PowerShell, se puede acceder directamente a las clases del entorno de ejecución [[.NET]] (`System.IO.Ports.SerialPort`) para abrir, leer y escribir datos binarios o texto sobre microcontroladores conectados vía USB:

```powershell
# 1. Identificar puertos COM disponibles en el host
[System.IO.Ports.SerialPort]::GetPortNames()

# 2. Instanciar y configurar el puerto serial (ejemplo: COM3 a 115200 baudios)
$port = New-Object System.IO.Ports.SerialPort "COM3", 115200, [System.IO.Ports.Parity]::None, 8, [System.IO.Ports.StopBits]::One
$port.ReadTimeout = 5000
$port.WriteTimeout = 2000
$port.Open()

Write-Host "[INFO] Puerto serial COM3 abierto exitosamente."

# 3. Lectura de telemetría de arranque del ESP32
try {
    while ($port.IsOpen) {
        $line = $port.ReadLine()
        Write-Host "[ESP32] $line"
    }
} catch [TimeoutException] {
    Write-Warning "[TIMEOUT] Espera agotada sin recibir datos."
} finally {
    # Garantizar cierre del descriptor para no bloquear el puerto
    $port.Close()
    $port.Dispose()
    Write-Host "[INFO] Puerto serial liberado."
}
```

El bloque `finally` asegura que la interfaz serie se libere en el driver del sistema operativo, evitando el error `Acceso denegado al puerto COM` en intentos posteriores.
